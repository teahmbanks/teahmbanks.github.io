# Feature Specification - Contact Page

> Use this specification together with `docs/ai/ai-spec.md`. The Module 16 rubric remains the grading authority.

## 1. Goal

Create an accessible public contact experience with LinkedIn access and a validated form that inserts messages into the Supabase `messages` table when public configuration is available.

## 2. Scope

### In scope

- Visible name, email, and message fields.
- Client validation, pending protection, success feedback, retained-input failure behavior, and missing-configuration fallback.
- Supabase insert payload limited to `name`, `email`, and `message`.
- LinkedIn access, responsive layouts, and identical behavior in every presentation mode.

### Out of scope

- Public message reading, editing, or deletion; admin authentication; spam services; file attachments; or exposing secret credentials.

## 3. Validation

- Trim surrounding whitespace.
- Name: required, maximum 100 characters.
- Email: required, valid email format, maximum 254 characters.
- Message: required, maximum 2,000 characters.
- Associate each error with its field and provide a summary-free first-error focus path through native labelled controls.

## 4. Supabase contract

- Use the existing shared browser client and table `messages`.
- Create the table and anonymous insert-only RLS policy with `supabase/messages.sql`.
- Insert only `{ name, email, message }`; IDs and timestamps are generated by Supabase.
- Disable duplicate submissions while pending.
- If configuration is missing, keep LinkedIn and the public page usable while clearly explaining that the form is temporarily unavailable.
- Retain all input after a failed insert and show a clear, non-sensitive error.
- Reset the form after a successful insert and clear feedback on the next edit.

## 5. Accessibility and responsive behavior

- Use one page-level heading, labelled regions, visible labels, `aria-describedby`, and programmatically distinct status/error feedback.
- Do not rely on color alone for required fields, errors, or submission state.
- Controls meet comfortable touch-target sizes and stack without horizontal overflow at 768px, 320px, and 200% zoom-equivalent widths.
- Presentation-mode changes must not reset an in-progress draft.

- [x] The global and feature specifications are reviewed before implementation.
- [x] Name, email, and message fields use visible labels and aligned validation limits.
- [ ] Valid submissions insert only the approved payload into `messages`.
- [ ] Pending, success, invalid-input, Supabase-failure, and missing-configuration states behave as specified. Missing configuration is locally verified; live states require Supabase.
- [x] LinkedIn remains available when the form cannot submit.
- [ ] Simple, Corporate, and Dramatic modes preserve the same draft, content, and behavior.
- [ ] Keyboard, focus, error association, status announcement, and reduced-motion behavior are verified.
- [ ] Desktop, 768px, 320px, and 200% zoom-equivalent reflow checks pass. Desktop, 768px, and 320px pass; 200% zoom remains.
